# PhotoAgent 1.4.1 — задание программисту 1С 8.2

Актуально для релиза **1.4.1**, 14.11.2026. Формат поэтапной передачи из 1.2.0 сохранён. В 1.4.0 введены ограничения кеша и `transfer_expired`, а в 1.4.1 — FIFO по отдельным фото и поле `expired_files`. Обработку 1С нужно дополнить этими правилами. PhotoAgent работает на рабочей станции Windows 10, клиент 1С — в RDP-сеансе Server 2008 R2. После каждого фото агент отдаёт отдельный JSON. 1С начинает загрузку сразу, пока оператор снимает следующие кадры. Исходник обработки 1С в репозитории отсутствует; её доработка выполняется отдельно по этому документу.

## 1. Каталоги

Корень на рабочей станции — `C:\psa_photos`. При перенаправленном диске C клиент 1С использует следующие пути.

| Назначение | Путь из RDP-сеанса |
|---|---|
| Задания | `\\tsclient\C\psa_photos\commands` |
| Уведомления и итоговые ответы | `\\tsclient\C\psa_photos\responses` |
| JPEG для поэтапной загрузки | `\\tsclient\C\psa_photos\transfer\<request_id>\<file>` |
| Старые рабочие JPEG для совместимости | `\\tsclient\C\psa_photos\photos\<document_number>\<file>` |

Работу с `\\tsclient` выполнять **на клиенте 1С в сеансе оператора**. Для клиент-серверной базы передавать прочитанные данные серверу штатным механизмом платформы. Чтение JSON и передачу двоичных данных реализовать средствами, совместимыми с установленным релизом 1С 8.2.

## 2. Задание — формат сохранён

Для каждой новой съёмки создать уникальный `request_id`, предпочтительно GUID, и сохранить связь с документом 1С.

```json
{
  "command": "capture_document",
  "request_id": "f3e1a292-7038-42b9-aaf7-4c65d019b859",
  "document_number": "PSA_12345"
}
```

| Команда | Съёмка |
|---|---|
| `capture_document` | Три фото: `lomo` — лицо, `passport` — паспорт, `registration` — прописка |
| `capture_extra` | Произвольное количество фото типа `extra`; Esc завершает сеанс успешно |

Все три поля обязательны. Идентификатор и номер документа должны быть безопасными именами Windows без `\ / : * ? " < > |`, `.` и `..`; использовать короткие значения без завершающих пробелов и точек.

Записать UTF-8 JSON в `commands\<request_id>.tmp`, закрыть и переименовать в `<request_id>.json`. Прямая запись `.json` поддерживается: агент опрашивает каталог каждые 500 мс и повторяет чтение занятых и недописанных файлов.

## 3. Уведомление после каждого фото

Файл `responses\<request_id>.photo.0001.json` публикуется **сразу после сохранения закрытого JPEG**, до следующего этапа съёмки. Номер `0001` соответствует `sequence`; следующие — `0002`, `0003` и т. д.

```json
{
  "status": "photo_ready",
  "request_id": "f3e1a292-7038-42b9-aaf7-4c65d019b859",
  "document_number": "PSA_12345",
  "sequence": 1,
  "photo_type": "lomo",
  "file": "PSA_12345_lomo.jpg",
  "relative_path": "transfer\\f3e1a292-7038-42b9-aaf7-4c65d019b859\\PSA_12345_lomo.jpg"
}
```

| Поле | Значение |
|---|---|
| `status` | Всегда `photo_ready` для такого уведомления |
| `request_id`, `document_number` | Связь с заданием и документом |
| `sequence` | Порядковый номер снимка **внутри запроса**, начиная с 1 |
| `photo_type` | `lomo`, `passport`, `registration` или `extra` |
| `file` | Имя JPEG; для дополнительных — `<document_number>_extra_001.jpg` и далее |
| `relative_path` | Путь к JPEG относительно `C:\psa_photos` |

Путь чтения из 1С — `\\tsclient\C\psa_photos\` + `relative_path`. Проверять, что он остаётся внутри `transfer\<request_id>`, не содержит абсолютного пути и `..`.

В JSON передаются метаданные, сам JPEG читается отдельным файлом. Снимки в `transfer` не перезаписываются следующими запросами, даже для того же документа. Поэтому медленная загрузка первого запроса может продолжаться во время новой съёмки. Для каждого дополнительного фото также сразу появляется отдельный JSON; ждать Esc не нужно.

Агент пишет JSON во временный `.tmp` и затем переименовывает. Обрабатывать только готовые `.photo.*.json`. Порядок перечисления файлов не гарантирован.

## 4. Итоговый ответ `.done`

После завершения съёмки появляется `responses\<request_id>.done`; затем агент удаляет задание. Совместимые поля сохранены, добавлен итоговый список готовых снимков.

| Поле | Содержание |
|---|---|
| `status` | `ok`, `error` или `busy` |
| `request_id`, `document_number` | Идентификаторы задания |
| `files` | Только для `ok`: прежний массив имён рабочих JPEG |
| `message` | Для `error` и `busy`: причина |
| `photo_count` | Для `ok` и `error`: число готовых снимков текущего запроса |
| `photos` | Для `ok` и `error`: массив объектов **того же формата, что отдельные `photo_ready`** |

Для основной успешной серии `photo_count = 3`. При отмене после первого фото — `status = "error"`, `photo_count = 1`, и `photos` содержит этот готовый снимок. При отмене до первого кадра массив пустой. Дополнительная съёмка через Esc может успешно завершиться с нулём снимков.

Крестик возвращает `message = "Некорректное завершение обработки задания"`. Таймаут — `Capture timeout`. При `busy` сообщение — `PhotoAgent is busy`; снимки в этот ответ не включаются. Логику строить по `status`, текст сообщения использовать для отображения.

**`ok` означает, что съёмка завершена. Загрузка в 1С завершена только после сохранения всех `photo_count` снимков.** Итоговый `photos` позволяет обнаружить уведомления, которые 1С ещё не увидела из-за задержки RDP.

Поле `files` оставлено для старой обработки, которая читает `photos\<document_number>`. Для `capture_extra` оно может включать снимки прошлых сеансов. **Новая обработка использует только `photo_ready` и итоговый `photos`, загружает по `relative_path` и повторно не обрабатывает `files`.**



Если нужно обслуживать PhotoAgent до версии 1.2.0, предусмотреть отдельный режим: при итоговом `ok` **без поля `photos`** загрузить прежний `files` из папки документа после `.done`. При наличии `photos` этот режим не использовать, даже если массив пустой: успешный `capture_extra` может содержать ноль новых снимков. В старом режиме до окончания загрузки не запускать повторную съёмку того же документа.

## 5. Очередь загрузки в 1С

1. До отправки задания сохранить его `request_id` и документ в постоянном состоянии обработки.
2. Начать таймерный опрос `<request_id>.photo.*.json` сразу после отправки задания, без ожидания `.done`.
3. Сопоставить `request_id` и `document_number` с исходным заданием; проверить положительный целый `sequence`, допустимый `photo_type`, имя JPEG и относительный путь. Добавить снимок в устойчивую очередь загрузки. Ключ идемпотентности — **`(request_id, sequence)`**. Повторное уведомление с тем же ключом не создаёт второе вложение. Для одинакового ключа метаданные должны совпадать.
4. Загружать JPEG из очереди по одному, по `sequence`. Во время сетевой передачи PhotoAgent продолжает фотографирование независимо от загрузчика. Следующие уведомления и JPEG остаются на диске.
5. Сохранять **содержимое JPEG**, а не ссылку на `\\tsclient`. Запись вложения и отметка `(request_id, sequence)` должны фиксироваться одной транзакцией либо идемпотентной записью под этим ключом. Только после фиксации считать снимок загруженным. При ошибке сети оставить очередь и уведомление, повторить чтение того же JPEG. Новое задание съёмки из-за ошибки передачи не создавать.
6. Удалить уведомление только после фиксации снимка. После этого при необходимости удалить сам JPEG из `transfer`. Служебные квитанции `transfer\<request_id>\photo.NNNN.json` оставить агенту.
7. При появлении `.done` добавить в очередь недостающие элементы `photos`, сверить `photo_count`, сохранить итоговый статус. При `error` уже готовые снимки остаются доступными; сохранить их как часть незавершённой серии, не отмечая фотокомплект полным.
8. Удалять `.done` после сохранения статуса и надёжной постановки всех его фото в очередь. Очередь должна переживать закрытие формы/перезапуск клиента. Помечать импорт завершённым после успешной загрузки всех ожидаемых снимков.

В интерфейсе удобно разделять прогресс: «снято 3, загружено 1». Удаление команды или появление `.done` не подтверждают передачу JPEG в базу 1С.

## 6. Ожидание и восстановление

- При отсутствии камеры показывается «подключите камеру»; задание продолжается после подключения. Таймаут PhotoAgent на время ожидания приостановлен. Уже готовые фото можно загружать в это время.
- При временной ошибке публикации JSON агент повторяет её каждые 500 мс во время съёмки. После съёмки повторяет публикацию без повторного фотографирования; `.done` не обгоняет ожидающие уведомления.
- При перезапуске с сохранившимся заданием и квитанциями агент восстанавливает уведомления и возвращает `error` о прерванной обработке. Старые JPEG сохраняются. Возможные повторы разобрать по `(request_id, sequence)`; для новой съёмки использовать новый GUID.
- `busy` можно повторить с тем же идентификатором после обработки и удаления ответа. Повтор активного запроса не запускает вторую съёмку.
- Свой таймаут 1С не отменяет работу PhotoAgent. Поздние уведомления и ответ нужно связать с исходным запросом; отмена съёмки выполняется закрытием окна агента.
- Временный кеш `transfer` автоматически очищается по сроку и объёму, в том числе для ещё не загруженных фото. По умолчанию — один месяц и 100 МБ; архив регулируется отдельно. Правила обработки очистки приведены ниже.

## 7. Срок и объём transfer

В `config.json` используются `transferRetentionMonths: 1` и `transferMaxMb: 100`. Мегабайт равен 1048576 байт. Отсутствующие, нулевые, отрицательные или некорректные значения заменяются на эти значения; ноль не отключает лимит. Правки применяются после перезапуска агента.

Очистка выполняется при запуске и раз в минуту. Сначала в порядке от старых к новым удаляются просроченные фото. Затем при превышении объёма применяется единая FIFO-очередь JPEG из всех папок по времени записи UTC, пока объём не уложится в лимит. Старое фото удаляется вместе со своими квитанциями; возраст пары определяется JPEG. Свежие снимки того же задания сохраняются. Служебные остатки очищаются по собственному времени записи. В объём входят JPEG, квитанции и остатки временных файлов. Активная съёмка и задания с открытыми читателями защищены. Если нельзя освободить место для JPEG и его квитанции, новая съёмка завершается с `status: error`; прежние готовые фото остаются в `photos`. Существующее превышение устраняется после освобождения занятых файлов.

**Очистка может удалить ещё не загруженные фото.** Перед удалением публикуется `responses\<request_id>.expired.json`:

```json
{
  "status": "transfer_expired",
  "request_id": "f3e1a292-7038-42b9-aaf7-4c65d019b859",
  "reason": "age",
  "expired_files": ["PSA_12345_lomo.jpg"],
  "expired_at": "2026-11-14T08:00:00.0000000Z",
  "message": "Временные файлы удалены из transfer по сроку или объёму"
}
```

`reason` — `age` или `size`, `expired_at` — время UTC. Проверять уведомление до начала загрузки и после ошибки чтения JPEG. Оно не является успешной загрузкой и не изменяет уже опубликованный `.done`.

Поле `expired_files` содержит накопленный список удалённых JPEG относительно каталога задания; для штатных фото это имена из поля `file` уведомления `photo_ready`. Сопоставлять имена без учёта регистра. Прекратить повторы только для перечисленных и ещё не сохранённых снимков, продолжая загрузку остальных. Зафиксировать неполную серию и сообщить оператору. Пустой `expired_files` не отменяет загрузку JPEG. Если поля нет, считать всё задание очищенным: так выглядят уведомления 1.4.0. Новая очистка не сужает уже опубликованные уведомления старого формата. Уже сохранённые вложения и отметки идемпотентности не откатывать. Для новой съёмки создать новый GUID. Не подставлять JPEG из `photos` или `archive`: там может быть другая версия документа.

Служебные `.expired.json` в `responses` **не удалять**: они предотвращают повторную съёмку старого запроса после очистки квитанций. Повтор такой команды без существующего `.done` получает `status: error`, `code: transfer_cache_expired`, `photo_count: 0`, `photos: []`. Если старый `.done` уже есть, он сохраняется; его `ok` не подтверждает бессрочную доступность кеша.

Для полностью загруженного запроса очистка не является ошибкой импорта. Если каталог через RDP недоступен и уведомление прочитать нельзя, применять сетевой повтор; одна ошибка сети не доказывает очистку.

## 8. Архив, конфигурация и обновление

Установщик Lite рассчитан на рабочую станцию Windows 10 с .NET Framework 4.8 или новее. Перед обновлением завершить съёмку и закрыть старый PhotoAgent через «Выход». Устанавливать под тем же оператором; затем запускать через новый ярлык. Данные в `C:\psa_photos` и назначения камер подхватываются. Старые переносные копии и созданные вручную задания автозапуска обслуживаются отдельно.

Конфигурация находится в `C:\psa_photos\config.json`. Фрагмент настроек архива:

```json
{
  "archiveRetentionMonths": 60,
  "archiveMaxGb": 100
}
```

Это фрагмент существующего файла, остальные настройки сохраняются. `60` означает текущий и 59 предыдущих календарных месяцев. Например, в ноябре 2026 года остаётся архив с декабря 2021 года. `archiveRetentionMonths` — положительное целое число; отсутствующее или ошибочное значение заменяется на `60`. Для применения изменений перезапустить PhotoAgent.

При первом запуске старый `archiveRetentionDays` удаляется; при отсутствии корректного срока в месяцах используется `60`. Заданный положительный срок в месяцах сохраняется. Исходный конфиг перед заменой записывается в `config.json.bak`; камеры и остальные поля сохраняются.

Архив `archive\YYYY-MM` очищается по месяцу в имени папки при запуске и далее раз в минуту. Дополнительный `archiveMaxGb: 100` может удалять старые месяцы раньше календарного срока; `0` отключает очистку по размеру. Эти ограничения **не очищают `photos` и `transfer`**. Источник поэтапной загрузки — `transfer`, а не архив. Удаление импортированных JPEG из `transfer` выполняет обработка 1С по правилам раздела 5; служебные квитанции оставляются агенту.

## 9. Приёмка

- При открытом предпросмотре второго этапа JSON и JPEG первого фото уже доступны; загрузка начинается до `.done`.
- Дополнительные кадры поступают отдельно до нажатия Esc.
- Медленное чтение фото первого запроса не мешает новой съёмке того же документа и не меняет читаемый файл.
- Крестик после одного кадра даёт `error` и итоговый список из одного снимка.
- После разрыва сети загрузка возобновляется без повторных вложений, пока снимки остаются в кеше.
- Очистка даёт `.expired.json` со списком удалённых JPEG; сохраняются свежие снимки старой папки, FIFO пересекает границы папок. Недоступные фото не запрашиваются бесконечно, остальные продолжают загружаться.
- Перезапуск PhotoAgent/1С сохраняет очередь, готовые снимки и связь с документом.

Пройдены 164 автоматические проверки: 25 проверок обмена, 22 проверки архива и миграции настроек, 31 проверка временного кеша, 21 проверка окон и камер с имитацией устройств, 65 проверок Lite-установки и сохранения данных на Windows Server 2022. Это проверки PhotoAgent; исходник конкретной обработки 1С не проверялся. Реальные USB-камеры, RDP и конкретную обработку 1С проверить на рабочем месте.
