# PhotoAgent 📸

[![NET Framework](https://img.shields.io/badge/.NET-5C2D91?style=badge&logo=.net&logoColor=white)](https://microsoft.com)
[![Platform](https://img.shields.io/badge/Platform-Windows-blue?logo=microsoft)](https://microsoft.com)
[![License](https://img.shields.io/badge/license-MIT-green)](LICENSE)

**PhotoAgent** — это специализированное фоновое Windows-приложение для автоматизации процессов фотофиксации клиентов и документов с помощью внешних веб-камер. Разработано для бесшовной интеграции с внутренними CRM/ERP системами через обмен файлами (File-based API).

---

## 🚀 Основной функционал

- **Фоновый режим работы**: Приложение сворачивается в системный трей (Tray) и не отвлекает оператора до момента поступления команды.
- **Управление через JSON (File API)** — проверка папки команд каждые 500 мс, включая файлы, созданные через перенаправленный диск RDP, и задания, оставшиеся до запуска агента.
- **Передача по готовности** — отдельное JSON-уведомление после каждого сохранённого JPEG. Загрузка в 1С идёт параллельно дальнейшей съёмке.
- **Интерактивный мастер настройки камер**: Удобное разделение ролей устройств (камера «Ломосдатчик» для лица и камера «Документ» для стола).
- **Полноэкранный захват поверх всех окон**: Окна съемки принудительно активируются поверх текущих окон пользователя для концентрации внимания.
- **Поддержка горячих клавиш**: Управление процессом без мыши (`Space`/`Enter` — снимок, `Esc` — отмена/выход).
- **Автоматическое обслуживание диска (архиватор)**: Ротация снимков, контроль квот хранилища (в Гб) и автоматическая очистка устаревших файлов по истечении срока хранения.
- **Автозапуск**: Самостоятельная регистрация в реестре Windows для запуска вместе с системой.

## 📁 Структура каталогов системы

При первом запуске приложение создает и использует следующую структуру папок на диске `C:\`:

```text
C:\psa_photos\
├── commands\      <- Сюда внешняя CRM кладет задания (.json)
├── responses\     <- Сюда агент возвращает отчеты выполнения (.done)
├── photos\        <- Временное хранилище текущих сессий съемки
├── archive\       <- Долговременный упорядоченный архив (по месяцам YYYY-MM)
├── logs\          <- Логи работы приложения
└── config.json    <- Файл конфигурации агента
```

## 🛠 Интеграционное API (JSON)

Начиная с версии **1.2.0** для медленных каналов используется поэтапная загрузка. Итоговый `.done` и совместимые имена файлов сохранены, поэтому прежняя обработка 1С продолжит работать с загрузкой всей серии после завершения. Для ранней загрузки обработку 1С нужно обновить.

### 1. Запрос на запуск съемки (`commands/`)
Чтобы инициировать процесс фотографирования, создайте в папке `C:\psa_photos\commands\` файл с расширением `.json` (например, `req_101.json`):

```json
{
  "command": "capture_document",
  "request_id": "req_2026_06_10_001",
  "document_number": "4512_890432"
}
```
*Допустимые команды (`command`):* `"capture_document"` (пакет из 3-х фото: лицо, паспорт, прописка) или `"capture_extra"` (дополнительные снимки).

Агент принимает файл после двух последовательных проверок с одинаковыми размером и временем изменения, когда файл можно открыть для исключительного чтения и разобрать как полную команду. Незавершённые и занятые файлы остаются в папке для следующей попытки. В журнале появляется сообщение `Command not ready; will retry`.

Для публикации задания из 1С предпочтительно записать и закрыть файл с временным расширением `.tmp`, затем переименовать его в `.json` в той же папке. Прямая запись `.json` также поддерживается. Папку обмена должен читать клиент 1С в RDP-сеансе оператора.

Каждой новой съёмке нужен уникальный `request_id`. Завершённый запрос получает прежний результат при повторном поступлении в пределах текущего запуска агента. Ответ `.done`, оставшийся на диске после перезапуска, также предотвращает повторную съёмку. Статус `busy` допускает повторную попытку с тем же идентификатором после получения и удаления ответа.

### 2. Готовность отдельного фото (`responses/`)

Сразу после сохранения снимка агент создаёт закрытый JPEG для передачи в `C:\psa_photos\transfer\<request_id>`, затем атомарно публикует отдельный UTF-8 JSON:

`responses\<request_id>.photo.0001.json`

```json
{
  "status": "photo_ready",
  "request_id": "req_2026_06_10_001",
  "document_number": "4512_890432",
  "sequence": 1,
  "photo_type": "lomo",
  "file": "4512_890432_lomo.jpg",
  "relative_path": "transfer\\req_2026_06_10_001\\4512_890432_lomo.jpg"
}
```

`sequence` начинается с 1 для каждого запроса. Типы основной серии — `lomo`, `passport`, `registration` в этом порядке. Для дополнительных кадров — `extra`; уведомление появляется при каждом нажатии съёмки, до завершения сеанса через Esc.

`relative_path` считается от `C:\psa_photos` рабочей станции. В RDP клиент 1С читает JPEG по `\\tsclient\C\psa_photos\<relative_path>`. Пути `\\tsclient` доступны в клиентском контексте сеанса оператора. Не использовать путь рабочей станции как локальный путь сервера 1С.

Передаваемый JPEG не перезаписывается следующими заданиями. Один и тот же документ при новом `request_id` получает другую папку передачи. Копирование по сети выполняет 1С; PhotoAgent не ждёт окончания этой операции и продолжает съёмку. Временные файлы `.tmp` нужно игнорировать.

### 3. Итоговый ответ (`responses/`)

Ниже показаны совместимые поля успешного ответа. В версии 1.2.0 дополнительно присутствуют `photo_count` и `photos`.
После завершения сессии агент удаляет файл команды и создает в папке `C:\psa_photos\responses\` файл ответа `[request_id].done`:

```json
{
  "status": "ok",
  "request_id": "req_2026_06_10_001",
  "document_number": "4512_890432",
  "files": [
    "4512_890432_lomo.jpg",
    "4512_890432_passport.jpg",
    "4512_890432_registration.jpg"
  ]
}
```

Если оператор уже занят съемкой, мгновенно вернется статус занятости:
```json
{
  "status": "busy",
  "request_id": "req_2026_06_10_001",
  "message": "PhotoAgent is busy"
}
```

---

При отмене, таймауте или ошибке камеры возвращается `.done` со статусом `error`, идентификатором запроса и полем `message`. Обработчик ответа в 1С должен учитывать этот статус. Файл команды удаляется после публикации ответа. Ответ сначала записывается во временный файл и переименовывается в `.done` после закрытия, чтобы 1С получала целый JSON.

Итоговые `ok` и `error` содержат `photo_count` — количество готовых снимков **этого запроса**, и `photos` — массив объектов точно такого же формата, как отдельные `photo_ready`. Массив содержит все готовые снимки, в том числе сохранённые до отмены. `busy` не является завершением активной съёмки и этих полей не содержит.

Уведомления всех готовых снимков публикуются до `.done`. При временной ошибке записи уведомление повторяется каждые 500 мс, в том числе во время ожидания камеры. После окончания съёмки публикация повторяется без повторного фотографирования; `.done` ждёт публикации всех уведомлений. Из-за задержек файлового доступа из RDP 1С всё равно должна сверяться с итоговым `photos`.

Прежнее поле `files` остаётся в `ok` и ссылается на рабочие файлы в `photos\<document_number>`. Для `capture_extra` оно может включать файлы прошлых сеансов. **Новая обработка загружает только `photo_ready`/`photos` текущего запроса по `relative_path` и не загружает `files` повторно.**

### 4. Очередь загрузки в 1С

1. До отправки задания сохранить связь уникального `request_id` с документом.
2. Пока оператор снимает, опрашивать `responses\<request_id>.photo.*.json`. Проверять идентификатор, документ, тип и относительный путь внутри `transfer\<request_id>`; запретить абсолютные пути и `..`.
3. Сохранять задания загрузки в устойчивую очередь. Ключ — пара `(request_id, sequence)`. Порядок выдачи файлов при перечислении не гарантирован; сортировать по `sequence`. Один загрузчик читает JPEG и сохраняет вложение в 1С, пока PhotoAgent продолжает съёмку.
4. Считать фото загруженным только после фиксации вложения и отметки этого ключа в 1С. При ошибке сети повторять ту же загрузку. Не запускать новую съёмку из-за ошибки копирования.
5. Удалять уведомление только после успешной фиксации. После этого при необходимости можно удалить сам JPEG из `transfer`. Служебные квитанции `transfer\<request_id>\photo.NNNN.json` оставить агенту: по ним он распознаёт запрос после перезапуска.
6. При появлении `.done` сначала добавить в очередь пропущенные элементы `photos`. `ok` означает завершение съёмки, а завершение импорта — только загрузку всех `photo_count` файлов. `error` означает неполную серию; уже готовые снимки остаются доступны и учитываются в 1С по прикладным правилам. Удалить `.done` после сохранения итогового статуса и надёжной постановки всех его снимков в очередь.

1С может читать первый снимок, пока оператор снимает второй и третий. Если загрузчик ещё занят, последующие JSON и JPEG остаются на диске. Не нужно ждать `.done`, чтобы начать загрузку. До подтверждённого импорта PhotoAgent автоматически не удаляет снимки из `transfer`; место освобождает обработка 1С после сохранения фото.

При перезапуске агента с незавершённой передачей и оставшимся заданием восстанавливаются квитанции готовых фото, повторно публикуются уведомления и возвращается `error` о прерванной обработке. Старые JPEG не перезаписываются. Повторы уведомлений обработать по тому же ключу. Для новой съёмки нужен новый `request_id`.

### 5. Камеры и отмена

Окна съёмки выполняются в основном STA-потоке приложения. Если назначенная для текущего этапа камера отсутствует или отключилась, на месте предпросмотра отображается «подключите камеру». Агент повторно проверяет её наличие каждые 500 мс. После подключения и получения первого кадра предпросмотр запускается в том же задании. Съёмка кнопкой, пробелом или Enter доступна при наличии кадра.

Для снимков паспорта и прописки используется один работающий предпросмотр камеры документов. Между этими этапами подключение остаётся открытым. После закрытия камеры её остановка учитывается всеми окнами и следующими заданиями, поэтому повторное открытие ожидает завершения освобождения драйвера.

На время ожидания камеры таймаут `captureTimeoutSec` приостанавливается. После подключения продолжается отсчёт оставшегося времени действий оператора. Проверка таймаута выполняется каждые 5 секунд. Задание сохраняет статус занятости во время ожидания.

Закрытие крестиком любого окна съёмки, включая дополнительные снимки, возвращает `status: error` и `message: "Некорректное завершение обработки задания"` в файле `[request_id].done`. В режиме дополнительных снимков Esc завершает съёмку успешно. При закрытии основного окна через Esc возвращается ошибка завершения.

## ⚙ Конфигурация (`config.json`)

Основные параметры работы приложения настраиваются в файле `C:\psa_photos\config.json`:

| Параметр | Тип | Описание | Значение по умолчанию |
| :--- | :--- | :--- | :--- |
| `captureTimeoutSec` | int | Таймаут действий пользователя без времени ожидания подключения камеры (сек) | `120` |
| `archiveRetentionDays`| int | Срок хранения фото в архиве до удаления (дней) | `365` |
| `archiveMaxGb` | double| Максимальный размер папки архива (Гб) | `100.0` |
| `alwaysOnTop` | bool | Поверх всех окон во время съемки | `true` |

## 💻 Требования для сборки и развертывания

- **IDE**: Visual Studio 2022 / 2026
- **Платформа**: .NET Framework 4.8
- **Язык**: C# 8.0+
- **Ключевые зависимости**: 
  - `AForge.Video.DirectShow` (для работы с камерами через API DirectShow).
  - `System.Web.Extensions` (для встроенной сериализации `JavaScriptSerializer`).

### Сборка проекта:
1. Клонируйте репозиторий `https://github.com/atvrs/PhotoAgent.git`.
2. Откройте проект `PhotoAgent/PhotoAgent.csproj` в Visual Studio.
3. Восстановите NuGet-пакеты.
4. Выберите конфигурацию `Release` и нажмите **Build** -> **Publish PhotoAgent**.

Для обычной сборки без локального сертификата ClickOnce выполните `msbuild PhotoAgent/PhotoAgent.csproj /p:Configuration=Release /p:SignManifests=false /p:GenerateManifests=false` после восстановления NuGet-пакетов.

Регрессионные проверки файлового обмена запускаются в Windows командой `powershell -ExecutionPolicy Bypass -File tests/Run-CommandTests.ps1`. Для них достаточно установленного .NET Framework 4.8. Физические камеры заменяются тестовым обработчиком. GitHub Actions собирает приложение, выполняет эти проверки и сохраняет архив сборки.

Проверки окон и подключения камер запускаются командой `powershell -ExecutionPolicy Bypass -File tests/Run-CameraTests.ps1` после восстановления пакетов, при доступном MSBuild из Visual Studio. Используются настоящие окна, обработчик задания и файловый ответ 1С с имитацией видеоустройства. Проверяются подключение каждой камеры по ходу задания, отключение и восстановление предпросмотра, повтор запуска после ошибки, приостановка таймаута и закрытие крестиком. Обе группы тестов выполняются в GitHub Actions.

Для проверки на рабочем месте запустите агент на Windows 10 и создайте задание из реальной 1С 8.2 через RDP. Проверьте открытие съёмки без перемещения файла, получение `.done`, повтор после занятого файла, отмену и таймаут. Текущий `capture_document` сохраняет три снимка с двух камер — лицо, паспорт и прописку.
